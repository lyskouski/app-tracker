\subsection{Emerging Design}

An entry point differs per each system:

\begin{lstlisting}
// Android, composeApp/src/androidMain/kotlin:
class MainActivity : ComponentActivity() {
  override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setContent { App() }
  }
}
// iOS, composeApp/src/iosMain/kotlin:
fun MainViewController() = ComposeUIViewController { App() }
// Desktop, composeApp/src/desktopMain/kotlin:
fun main() = application {
  Window(onCloseRequest = ::exitApplication) { App() }
}
// Web, composeApp/src/wasmJsMain/kotlin/main.kt:
fun main() {
  CanvasBasedWindow(canvasElementId = "ComposeTarget") { App() }
}
\end{lstlisting}

\noindent A core entry point is \q{shared/src/App.kt}-file for our application:

\noindent SQLDelight provides a shared Kotlin database API with platform-specific drivers.
The shared module can use the runtime across Android, iOS, desktop, and Kotlin/Wasm; the web app
gets its Web Worker driver transitively from shared. The Web Worker driver requires a worker
implementation before it can open a database.
 
In our version catalog, libs.versions.toml, add:

\begin{lstlisting}
// ./libs.versions.toml
[versions]
sqldelight = "2.3.2"

[libraries]
sqldelight-runtime = { module = "app.cash.sqldelight:runtime", version.ref = "sqldelight" }
sqldelight-android-driver = { module = "app.cash.sqldelight:android-driver", version.ref = "sqldelight" }
sqldelight-native-driver = { module = "app.cash.sqldelight:native-driver", version.ref = "sqldelight" }
sqldelight-jdbc-driver = { module = "app.cash.sqldelight:sqlite-driver", version.ref = "sqldelight" }
sqldelight-web-worker-driver = { module = "app.cash.sqldelight:web-worker-driver", version.ref = "sqldelight" }
\end{lstlisting}

Add the shared runtime and platform-specific drivers to the module:

\begin{lstlisting}[language=yaml]
# ./shared/module.yaml
dependencies:
  - $libs.sqldelight.runtime

dependencies@android:
  - $libs.sqldelight.android.driver

dependencies@jvm:
  - $libs.sqldelight.jdbc.driver

dependencies@native:
  - $libs.sqldelight.native.driver

dependencies@wasmJs:
  - $libs.sqldelight.web.worker.driver
\end{lstlisting}

\paragraph{Gradle build.}
The Kotlin Toolchain (\texttt{./kotlin}) cannot apply the SQLDelight Gradle plugin, so it never
generates the \texttt{Database} class, and it cannot declare the npm dependencies the web
worker needs. A parallel Gradle build was therefore added (\texttt{settings.gradle.kts},
\texttt{build.gradle.kts}, \texttt{gradle.properties}, the Gradle wrapper 9.3.1 with AGP 9.1.0,
and a \texttt{build.gradle.kts} in each of \texttt{shared}, \texttt{androidApp},
\texttt{desktopApp}, \texttt{iosApp}, \texttt{webApp}). It reuses the same
\texttt{libs.versions.toml} (extended with \texttt{kotlinx-datetime},
\texttt{kotlinx-coroutines-core}, \texttt{sqldelight-async-extensions} and a \texttt{[plugins]}
section) and maps the existing source layout (\texttt{src}, \texttt{src@jvm}, \ldots).
The Toolchain files are kept; \texttt{shared/module.yaml} additionally declares
\texttt{sqldelight.async.extensions}, \texttt{kotlinx.datetime} and \texttt{kotlinx.coroutines.core}.
Applications that use the generated database must be built and run with Gradle:

\begin{lstlisting}[language=bash]
./gradlew :desktopApp:run
./gradlew :androidApp:assembleDebug
./gradlew :webApp:wasmJsBrowserDevelopmentRun
\end{lstlisting}

\paragraph{Schema and code generation.}
The SQLDelight plugin is configured in \texttt{shared/build.gradle.kts}:

\begin{lstlisting}
sqldelight {
    databases {
        create("Database") {
            packageName = "com.tercad.zwyka.infrastructures"
            generateAsync = true
        }
    }
}
\end{lstlisting}

\noindent The schema lives in
\texttt{shared/src/commonMain/sqldelight/com/tercad/zwyka/infrastructures/Database.sq}:
tables \texttt{Habit(id, title)} and \texttt{DayState(habitId, date, mark)}, queries
\texttt{selectAllHabits}, \texttt{insertHabit}, \texttt{selectAllDayStates},
\texttt{insertDayState}, and seed \texttt{INSERT}s replacing the former hardcoded values.
Asynchronous generation is required by the Web Worker driver; synchronous drivers wrap the
schema with \texttt{Database.Schema.synchronous()}. Identifiers in \texttt{Habit},
\texttt{DayState} and \texttt{CellKey} are \texttt{Long}, matching SQLDelight's INTEGER mapping.

\paragraph{Drivers per platform.}
Android uses \texttt{AndroidSqliteDriver}, desktop \texttt{JdbcSqliteDriver} (file
\texttt{\textasciitilde/.zwyka.db}), iOS \texttt{NativeSqliteDriver}, and the web app
\texttt{WebWorkerDriver}. The web worker (\texttt{webApp/sqljs/sqljs.worker.js}) runs SQL.js
and persists the database in IndexedDB; \texttt{webApp/webpack.config.d/sqljs.js} copies
\texttt{sql-wasm.wasm} to the output. The web entry point creates the worker in a top-level
function (Kotlin/Wasm requires \texttt{js()} in that position) and initializes the schema via
\texttt{PRAGMA user_version}.

\paragraph{UI wiring.}
\texttt{App} accepts an optional \texttt{Database} and an \texttt{initializeDatabase} callback
and passes them to \texttt{HomePage}. \texttt{HomePageContent} initializes the database in a
\texttt{LaunchedEffect}, loads habits and day states with \texttt{awaitAsList()}, and renders
the states Loading, Loaded and Failed. Dates are computed from \texttt{kotlin.time.Clock}
(today$-66$ \ldots today$+5$).
